# 登录后是否该用左右结构？

一份针对当前固定侧栏（`w-[15.5rem]` = 248px，`md` 断点起常驻）的论证。

---

## 结论先行

**当前的左右结构配置不合理，但不是因为「左右结构」本身错，而是三个具体问题：**

1. 侧栏在 `md`(768px) 就出现，那个宽度下它吃掉 54% 的可用空间
2. 侧栏承载的是低频入口，高频动作一个都没覆盖
3. 内容区 `max-w-7xl` 与侧栏抢宽度，两者在 1280px 以下持续冲突

建议：**保留左右结构，但把出现断点从 `md` 提到 `lg`(1024px)，并重新分配侧栏的内容。**

---

## 一、空间成本的量化

侧栏固定 248px。各页面内容宽度上限与实际渲染宽度：

| 视口 | 可用宽（减侧栏与内边距） | 群组详情 `max-w-7xl` 实际 | 状态 |
| --- | --- | --- | --- |
| 768px | 456px | 456px | **被压缩 824px** |
| 1024px | 712px | 712px | **被压缩 568px** |
| 1280px | 968px | 968px | 被压缩 312px |
| 1440px | 1128px | 1128px | 被压缩 152px |
| 1920px | 1608px | 1280px | 右侧空白 328px |

两个结论：

- **768–1280px 之间，内容区一直在被侧栏挤压**。这不是一个窄区间，而是笔记本电脑的主力分辨率带。
- 在 768px 上，456px 的内容区比一台 iPhone 15 Pro Max 的宽度（430px）只多 26px。**用了桌面布局，却得到手机的可用宽度。**

### 这个压缩有实际后果吗？

有，而且是自伤。结算汇总表在 `md` 起按 4–5 列网格排布——**和侧栏出现的断点完全相同**。两者叠加后每列实际宽度：

| 视口 | 卡片内宽 | 成员列 | 数字列 | 状态 |
| --- | --- | --- | --- | --- |
| 768px | 424px | 110px | **79px** | 严重不足 |
| 900px | 556px | 144px | **103px** | 不足 |
| 1024px | 680px | 176px | 126px | 勉强 |
| 1280px | 936px | 243px | 173px | 舒适 |

金额格式是 `CNY 1,234.56`，等宽字体下约需 110px。**768–1024px 全区间数字列都装不下，768px 时只有 79px。**

刚刚才把这张表从「双份 markup + 横向滚动」修成单树响应式，结果侧栏在同一个断点把它重新挤坏。这是两个改动各自合理、叠加后失效的典型例子。

---

## 二、侧栏装的是什么

固定项只有三个，加一个动态群组列表：

| 入口 | 频次判断 |
| --- | --- |
| 我的群组 | 中频（切换群组时） |
| 新建群组 | **低频**（一个群组用几周到几个月） |
| 账户 | **极低频**（只有身份信息与危险区） |
| 群组列表 | 中频 |

而用户在这个产品里的高频动作是：

| 动作 | 当前位置 |
| --- | --- |
| 记一笔 | 页内按钮 / 移动端底栏 — **不在侧栏** |
| 看账单流 | 群组详情 Tab — **不在侧栏** |
| 看结算 | 群组详情 Tab — **不在侧栏** |
| 改群组设置 | 群组详情 Tab — **不在侧栏** |

**248px 的常驻空间，换来的是三个低中频入口。所有高频动作都在第二层，侧栏一个都没覆盖。**

---

## 三、导航其实是两层，侧栏只做了一层

```
第一层（侧栏）    我的群组 · 新建群组 · 账户 · 群组 A/B/C
第二层（Tab）     账单 · 结算 · 设置
```

这是典型的「侧栏 + Tab」双层导航。问题在于：

- **第二层才是用户真正停留的地方**。打开 app → 进某个群组 → 在三个 Tab 间来回。
- 第一层在这个流程里只用了一次（选群组），之后长期闲置。
- 侧栏却为这个「用一次」的动作常驻 248px。

对比一下：如果把群组切换收进头部下拉（移动端已经这么做了），第一层的成本从 248px 常驻降到 0，只在需要时展开。

---

## 四、反方论点（为什么不该直接删掉侧栏）

我不认为应该删。理由：

**1. 群组切换确实需要低摩擦**
多群组用户（旅行 + 合租 + 同事聚餐）在群组间切换是真实场景。侧栏让这个动作零跳转。移动端因为空间受限只能用下拉，桌面端有空间就不该退化。

**2. 侧栏提供位置感**
高亮当前群组，用户始终知道自己在哪。Tab 只能表达「在群组内的哪一层」，表达不了「在哪个群组」。

**3. 记账类产品的同类实践**
这类「多账本 + 账本内多视图」的结构，侧栏是成熟解法。用户对左侧列表有既定预期。

**4. 内容本身不需要那么宽**
账单流是列表，单行信息密度有上限。`max-w-7xl`(1280px) 对一个列表来说本来就偏宽——一行拉到 1280px，视线从标题扫到金额要横跨整个屏幕，反而降低可读性。**这一条其实反过来说明：不是侧栏太宽，是内容区上限设得太随意。**

---

## 五、具体建议

### 建议 1：断点从 `md` 提到 `lg`（必要）

768–1024px 区间取消侧栏，改用顶部导航或头部群组切换器。这个区间给内容 100% 宽度，汇总表才有呼吸空间。

代价：`lg` 以下失去侧栏的位置感。可用头部的群组切换器补偿（移动端已实现，直接复用）。

### 建议 2：重新分配侧栏内容（建议）

把「账户」这类极低频入口从主导航降级到底部区域（现在已经在底部了，可以更弱化），把节省的注意力给群组列表。

更进一步：**考虑把群组详情的三个 Tab 提到侧栏的二级**，让侧栏真正覆盖高频动作：

```
我的群组
新建群组
─────────
周末出游          ← 当前群组
  账单
  结算
  设置
上海合租
日本行
```

这样侧栏从「只做一层」变成「覆盖两层」，248px 的成本才对得起收益。但这会与现有 Tab 组件冲突，改动不小。

### 建议 3：收紧内容区上限（建议）

`max-w-7xl`(1280px) 对列表型内容偏宽。群组详情改 `max-w-6xl`(1152px) 或 `max-w-5xl`(1024px)，减少与侧栏抢空间的冲突，同时提升行内可读性。

---

## 六、如果选择完全去掉侧栏

不推荐，但如果要做，替代方案是**顶部导航 + 群组切换器**：

```
[AAEasy]  [周末出游 ▾]              [账单 结算 设置]      [☰]
```

优点：内容区 100% 宽度；导航层级一目了然；与移动端头部结构一致，代码可共用。

缺点：失去群组列表的一览性；顶部横向空间有限，群组名长时容易挤。
